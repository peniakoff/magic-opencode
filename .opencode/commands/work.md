Own this local repository task end to end using the smallest effective workflow: $ARGUMENTS

Establish acceptance criteria and inspect repository guidance/current state. Resolve version-sensitive APIs, unknown behavior locations, broad consumer impact, and other discovery questions with orchestrator tools or `research-explorer` before dispatching a writer. Use `architect` only when material design decisions require it.

Create an ordered implementation-slice plan before calling `implementer`. Sequential slices are the default. Each writer slice should be cohesive, preferably about 1-6 files, have an exact allowed scope, contain already-verified external/API facts, include focused tests where practical, and be small enough for the implementer to reach its first edit within 8 tool calls. Do not send one large brief containing research, implementation, broad tests, documentation, and release work when those concerns can be split safely.

Immediately after the slice plan is stable and before the first implementer call, materialize it with `todowrite` in the parent orchestrator session so the right panel shows user-visible progress. Keep the list concise, normally 4-10 items: one item per meaningful implementation slice plus the remaining major gates such as validation and final review. Before starting a phase, mark its item `in_progress`; after verifying its result, mark it `completed` before moving on. If research, a repair, `SCOPE_TOO_LARGE`, or another event changes the plan, update the list immediately instead of leaving obsolete or stale items. For two parallel lanes use one parent item such as `Implement parallel slices A + B`. The orchestrator owns this list; a subagent todo list is not a substitute. Before the final response, make one final `todowrite` update so no stale `in_progress` item remains.

The implementer is write-only in purpose: never ask it to research Context7/web docs, inspect `node_modules`, establish architecture, or broadly audit the repository. Handle `NEEDS_RESEARCH` by resolving the exact question outside the writer, updating the todo plan, and redispatching a small write-ready slice. Handle `SCOPE_TOO_LARGE` by splitting the slice and replacing the corresponding todo item. If a writer returns empty output, hits a step limit, or makes no edits where edits were expected, do not replay the same brief unchanged; reuse any verified facts, shrink the task, and update progress accordingly.

After every sequential slice, inspect the actual root diff and verify scope before marking that slice completed and dispatching the next writer. Later slices may intentionally consume earlier uncommitted root changes when the plan says so. Use at most two parallel implementers only when the orchestrator proves two write-ready slices have disjoint scopes, no shared mutable contract, and no dependency on each other's uncommitted output; isolate them through the trusted worktree workflow and integrate only reviewed lanes.

Before running changed repository code, preliminarily inspect/review executable inputs. Mark validation `in_progress`, then use repository-native checks in increasing cost order. If formatting fails only because task-owned changed files need deterministic formatting, run `bash .opencode/scripts/format-changed.sh <exact-failing-path>...` and rerun the formatting check; do not delegate whitespace, wrapping, comma, or import-layout fixes to an implementer. Use `test-debugger` for ambiguous failures, `browser-qa` for supplementary exploratory user-flow checks, `security-reviewer` for sensitive boundaries, and `reviewer` for substantial/risky final diffs. Route confirmed semantic/code corrections through another bounded implementer slice and reflect the repair in the todo list.

Mark final review `in_progress` before the final review gate and complete it only when no actionable finding remains. Do not commit, push, publish, deploy, or alter remote resources unless I explicitly requested it. Use `/implement <issue-url>` for the complete GitHub delivery workflow.
